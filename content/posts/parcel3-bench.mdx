## 1. 「最多快 100 倍」先看它在测什么

[Parcel 3 alpha 公告](https://v3.parceljs.org/blog/v3-alpha/)写于 2026-11-04。第一段就把范围划清楚了：

> Today we're releasing the first alpha of Parcel 3, a ground up rewrite of Parcel in Rust. It is up to 100x faster than v2, and supports native plugins written in Rust, Go, Swift, or C, as well as a custom runtime for JavaScript and TypeScript plugins.

稍后又补了一句更具体的口径：「up to 100x faster builds using the same underlying compilers as v2, only changing the core。」也就是说，他们没有换掉 v2 里已经用 Rust 重写过的那些编译器（基于 SWC 的 JavaScript 编译器、Lightning CSS，以及后来的 HTML / SVG transformer），只换了核心。

公告里的对比图测的是 React Spectrum 这个大型 TypeScript monorepo 的**冷开发构建**，并写了三个入口的规模：Storybook 约 100 个入口，带 JS macros，自定义插件为 Parcel 3 移植到了 Rust；文档站约 340 页，用了 React Server Components、MDX、Tailwind 和自定义插件；library build 约 160 个包，输出超过 14,000 个文件。图里的柱状数值只出现在图片里，本文没有从截图里估读毫秒数。能引用的只有上面这些文字，以及「up to 100x」本身——这是上限描述，不是对任意项目、任意构建模式的承诺。

安装方式公告和[迁移指南](https://v3.parceljs.org/migration/parcel-2/)说的是同一套：日常可以把依赖换成 `parcel@next`（本文写作时指向 `3.0.0-alpha.2`）；如果想和 Parcel 2 并排，就装 `@parcel/parcel3`，用 `parcel3` 命令，并给一个不同的 `--dist-dir`。

## 2. Parcel 2：Node 核心，Rust 编译器

公告把 v2 的瓶颈写得很具体。v2 已经把 JavaScript 编译器（基于 SWC）、Lightning CSS、HTML / SVG transformer 和 optimizer 陆续改成了 Rust，但**核心仍是 JavaScript**：

> This limited our maximum possible performance due to lack of shared memory between threads, high memory usage, garbage collection, and the cost of serializing values between workers and languages.

这四件事——线程之间不能共享内存、内存占用高、垃圾回收、worker 与跨语言边界上的序列化——是官方对自己为什么要重写核心的解释，不是我事后推测。

我把它理解成一张分层图。最外层是一个 Node 进程：JavaScript 核心负责编排构建、加载配置、跑插件管线。Parcel 2 把几乎每一种能力都拆成独立的 npm 插件包，模块化很好，但公告自己也说，代价是「hundreds of dependencies that you needed to upgrade and maintain」。再往下是 worker 进程池：变换会被派到其他进程里做，进程之间不能直接共享对象，数据要先序列化再传过去。最底层才是已经用 Rust 重写的编译器；JavaScript 核心调用它们时，还要再跨一次语言边界。公告把「workers」和「languages」并列写进序列化成本，指的就是这两道缝。

这能解释为什么 v2 后来会「heavily invested in disk caching and incremental builds」。底层如果慢，把变换结果记到磁盘、下次尽可能复用，是很划算的；但记账、失效追踪本身也有开销，还会引入一批过期缓存的 bug。核心一旦变快，这套缓存哲学就不再是免费的加速器，而可能变成新的瓶颈。

## 3. Parcel 3：整棵树变成一个原生进程

v3 的对策写在同一段：

> Parcel v3 is an entirely self-contained Rust binary, with no dependency on Node at all. Everything from the CLI and dev server, to the transformers, bundler, optimizers, and everything in between is now fully native.

一边是 Node 进程里的 JavaScript 核心去调度 Rust 编译器，一边是单一的原生二进制把整条管线都放进同一个地址空间。差异可以画成下面这样：

![Parcel 2 的 Node 进程（JS 核心、插件 API、Worker Farm）通过跨语言边界调用 Rust 编译器，对比 Parcel 3 的单一 Rust 二进制（内置 resolver、transformer、bundler、packager）](/posts/parcel3-bench/arch.svg)

「不依赖 Node」带来的直接后果，是线程可以共享内存、没有 JavaScript 核心的 GC、也不再为了派活给 worker 或跨语言调用而反复序列化。公告把收益写成「efficiently take full advantage of modern multi-core hardware」，并强调这是「only changing the core」、编译器底子没换。

管线本身也被收进二进制里。公告说常见 Web 语言都是开箱即用的（HTML、CSS、JavaScript、TypeScript、SVG、图片转换与优化、RSS / Atom、web manifest 等），并且「Newly added is native support for Tailwind (without PostCSS), React Compiler, MDX, SVG → JSX, and glob imports。」这些是能力清单，不是「默认全开」：[React 文档](https://v3.parceljs.org/recipes/react/)里 React Compiler 要在 `.parcelrc` 里给 `@parcel/transformer-js` 设 `reactCompiler: true` 才会启用；Tailwind 也要显式加上 `@parcel/transformer-tailwind`。MDX 则是[开箱即用](https://v3.parceljs.org/languages/mdx/)。[迁移指南](https://v3.parceljs.org/migration/parcel-2/)还写明：packager 和 runtime 不再是单独的插件类型，「packaging is now handled by Parcel itself」。

缓存策略跟着变了。公告的结论是：

> Parcel 3 uses a significantly simpler architecture, optimizing for the fastest possible cold builds rather than paying for the overhead of caching. We still support incremental in-memory rebuilds, but don't need to write each transformation result to disk, or perfectly track all possible invalidations.

[迁移指南](https://v3.parceljs.org/migration/parcel-2/)把这落实成一句操作说明：「Parcel 3 is fast enough that it no longer writes a cache to disk. You can delete the `.parcel-cache` directory」。CLI 上也删掉了 `--no-cache` 和 `--cache-dir`。所以第二次 `parcel3 build` 并不是「热构建」，它只是又一次冷构建；真正的增量发生在 `parcel3 serve` 的进程内重建。

插件模型也拆成了两层。因为二进制本身不依赖 Node，JavaScript / TypeScript 插件和 macros 跑在嵌入的 QuickJS 里，「intentionally lacks things like network access」；需要极限性能时，官方建议写原生插件（Rust、Go、Swift，或任何支持 C ABI 的语言）。这并不是「再也不能写 JS 插件」，而是：简单、不常跑的插件还可以用 JS，但执行环境和 Node 并不等价。配置则集中到 `.parcelrc`：公告说这样不只是好找，也避免了构建过程中反复在文件系统上搜 `.babelrc`、`.postcssrc` 这类文件。

分包和 tree-shaking 也有变化。公告写，在一个 450 页的站点上相对 v2「64% fewer HTTP requests per page」「10% less transferred bytes per page」，来自改进后的分包合并成本模型——本文没有复现这种页面级 HTTP 请求对比，只把它当作官方自己的数字。与此同时，JavaScript 的 scope hoisting 被去掉了，官方的理由是「reduces bug surface area while retaining most of the benefit of tree shaking, and enabling features like top-level await」。[迁移指南](https://v3.parceljs.org/migration/parcel-2/)写得更直白：「Parcel 3 no longer concatenates modules into a single scope ("scope hoisting"). Tree shaking is still supported, and unused exports are removed from your production builds。」

## 4. 这些取舍要付的账

独立二进制不是免费的升级。我看到的代价主要有三块。

第一块是插件生态。Parcel 2 那套「每个能力一个 npm 包、在 Node 里随便 `require`」的模型，和「单一 Rust 进程加嵌入式 JS 运行时」没法无缝对接。迁移指南列了一批默认配置里不再包含的插件（Babel、PostCSS、Sass、Less 等），也删掉了自动安装依赖；JS 插件还失去了网络、定时器和 `child_process` 这类 API。现有的 Parcel 2 插件需要按新 API 改，复杂或热路径上的插件更适合写成原生插件。alpha 阶段公告自己列了还没做完的部分：compressor 插件、`.d.ts` 生成、自定义 bundler 插件、可编程的 JavaScript API，以及一些 known issues。如果你的项目深度绑在这些缺口上，现在还不是迁过去的时候。

第二块是产物形态。去掉 scope hoisting 之后，模块不再被拼进同一个作用域，tree-shaking 仍在，但「大多数收益」不等于「体积不变」。另外，[生产文档](https://v3.parceljs.org/features/production/)写明 Parcel 3 会在每个 HTML 页面或入口 bundle 里放一份 manifest，用稳定的 bundle id 去引用带内容哈希的文件名，以避免级联失效：更新一个异步页面时，不必让中间 bundle 的文件名跟着 cascade。这是用入口 HTML 的体积换缓存命中率，不是漏压缩。

第三块是成熟度。公告写「the Parcel 3 binary is less than 30 MB with zero npm dependencies」，并说这比 Parcel 2「total install size (including dependencies) was ~120 MB」小 4 倍。我在 Linux x64 上解出的 `@parcel/parcel3-linux-x64/parcel` 是约 36.2 MiB 的 ELF，用 gzip -6 压完约 14.5 MiB；未压缩文件比「不到 30 MB」略大，公告可能指发布体积或另一套压缩口径，我没有拆他们的 npm tarball 核对。alpha 本身也意味着行为还可能变。

## 5. 中型应用上，这些取舍长什么样

数字只用来对照上面这些设计选择，不是本文的主角。我用同一份 React 19 + TypeScript 的单页应用，对比了 `parcel@2.16.4`、`@parcel/parcel3@3.0.0-alpha.2` 和 `@rspack/core@2.3.1`：24 条懒加载路由，一共 390 个源文件。三套生产构建都开 minify、都关 source map，`browserslist` 统一为 `> 0.5%, last 2 versions, not dead`。每组 5 次取中位数；冷构建每次先清掉该工具的缓存目录。没有打开 React Compiler，也没有用 Tailwind 或 MDX，为的是三边编译同一份源码。

![同一份中型 React 应用上，Parcel 2、Rspack 与 Parcel 3 的生产冷构建时间和峰值内存](/posts/parcel3-bench/build-cost.svg)

|            |  冷构建 | 峰值 RSS | JS gzip | 开发启动 | HMR（日志） |
| ---------- | ------: | -------: | ------: | -------: | ----------: |
| Parcel 2   | 1.595 s |  831 MiB |  137 KB |  1.218 s |       58 ms |
| Rspack 2.3 | 0.325 s |  175 MiB |  123 KB |  0.242 s |       17 ms |
| Parcel 3   | 0.112 s |  126 MiB |  185 KB |  0.102 s |      4.5 ms |

冷构建上，Parcel 3 相对 Parcel 2 是 1.595 / 0.112 ≈ 14.2 倍，不是 100 倍；相对 Rspack 大约 2.9 倍。峰值内存从约 831 MiB 降到约 126 MiB，大约是 6.6 倍。开发服务器启动和改一个已纳入编译图的叶子文件后的重建，方向也一致。

为什么远不到 100 倍，我认为有三件可以核对、不必发明的原因。

1. **官方测的不是这种项目。** 他们写的是 React Spectrum 的冷*开发*构建：上百个 Storybook 入口、340 页带 RSC / MDX / Tailwind 的文档站、160 个包输出一万四千个文件，而且还带「移植到 Rust 的自定义插件」。这里是 390 个模块的单一 SPA、生产模式、没有自定义插件、没有 MDX / Tailwind / macros。规模差一个数量级以上，100× 这种上限出现在更大、插件更重的图上并不奇怪。
2. **官方比的是「只换核心、编译器相同」。** 这句话同样适用于我们：三边的 JS 压缩 / 转译底子都是 SWC 家族（Parcel 2 / 3 用 SWC 压缩 JS，Rspack 2.3 还换成了 [SWC Next 解析器](https://rspack.rs/blog/announcing-2-3)）。核心换成 Rust 之后，剩下的时间会越来越接近「读盘 + 跑 SWC + 写盘」的下限。这份应用上 Parcel 2 本身只要 1.6 秒，再快 100 倍意味着 16 毫秒——只够付进程启动和扫一遍 390 个文件。Parcel 3 落到 112 毫秒，已经开始撞上这类固定成本。
3. **「up to」是上限。** 公告没有说中型 SPA 的生产构建也会看到 100 倍。把 14.2 写成「没达到承诺」并不准确；把它写成「在这份项目、这种模式下测到的倍数」才准确。

GNU time 记录的冷构建 CPU 占用，三家都明显大于 100%（Parcel 3 约 299%–318%，Parcel 2 约 282%–334%，Rspack 约 183%–194%）。也就是说并不是「只有 Rust 核心才会并行」；这份应用也远没有把 8 核吃满。墙钟上的 14 倍，更多来自单次工作更便宜（没有 JS 核心、没有跨 worker 序列化、也没有磁盘缓存记账），而不是并行度突然高了一个数量级。这和公告对自己瓶颈的解释是同一方向，但我没有单独拆出「序列化到底占了多少毫秒」，所以只把它当作定性解释。

缓存哲学也能在第二次 `build` 里看到。Parcel 2 的磁盘缓存把生产构建从 1.595 s 收到 0.568 s；Rspack 在 production 默认不写持久缓存（[文档](https://rspack.rs/config/cache)写明 development 默认内存缓存、production 默认 `false`），显式打开 `cache: { type: "persistent" }` 之后，第二次构建是 0.137 s。Parcel 3 的「热」中位数是 0.124 s，甚至略慢于冷构建的 0.112 s——按文档它根本不写 `.parcel-cache`，两次都是完整构建，0.01 s 的差别落在 5 次样本的噪声里。如果生产流水线每次都是干净的 CI runner，针对冷构建优化、不再维护磁盘缓存，直接对上使用方式；如果是本机反复跑 `build`，磁盘缓存仍然有用，只是在这份中型应用上，它们追不上 Parcel 3 重跑一次冷构建的速度。

体积是另一张成绩单。Parcel 3 的 JS raw 比 Parcel 2 大约重 29%（514,447 → 664,885 字节），gzip 后大约重 36%（136,665 → 185,427 字节）。这和官方去掉 scope hoisting 的行为变化相对应，但本次没有做逐模块对比来证明体积差全部来自这件事，所以只能说到这一步。Rspack 仍走 webpack 那一套 module concatenation / splitChunks，JS gzip 是三家里最小的。Parcel 3 的入口 HTML 从 300 字节量级变成了约 2.5 KB，里面有一份 `data-parcel-manifest` JSON，和生产文档里的 cascade invalidation 说明对得上。

要把同一份源码接进三个打包器，默认行为也不完全一样。Parcel 2 默认没有完整跟随 package `exports`，要给 `@parcel/resolver-default` 加上 `packageExports: true` 才能解析 `react-router@7`（迁移指南写 Parcel 3「Package `exports` are always enabled」）；Rspack 的 CSS Modules 默认导出的是具名绑定，要对齐 Parcel 的默认对象导出需要 `namedExports: false`；`rspack serve` 在只针对 web 的编译器上，若用户没写 `lazyCompilation`，会默认给动态 import 打开延迟编译，懒路由里的文件改了不会马上重建。这些不是谁对谁错，而是「公平对比」本身就要付的配置税。

测量脚本、配置和原始 CSV 在 [`labs/parcel3-bench/`](https://github.com/Lios09/Blog/tree/main/labs/parcel3-bench)。数字来自每组 5 次取中位数的墙钟时间和 GNU time 峰值 RSS；本文不再展开复现步骤。

## 6. 什么时候选 Parcel 3、Rspack 还是 Parcel 2

我会这样看这三种工具。

如果项目主要用 Parcel 已经内置的那些语言，构建跑在干净的 CI runner 上，在意冷启动和内存，并且能接受 alpha 的缺口、以及目前更大的 JS 产物，Parcel 3 的方向是对的。它把「核心停在 JavaScript」这件事整个拿掉了，缓存哲学也和 CI 的使用方式对齐。前提是你不依赖需要完整 Node 的 JS 插件，也不急着要 compressor、`.d.ts` 生成或可编程 API。

如果已经在 webpack 生态里，或者更在意第一次下载的 gzip 体积，Rspack 仍然非常有竞争力。这份应用上它的 JS gzip 最小，打开 persistent cache 之后本机反复构建也接近 Parcel 3 再跑一次冷构建的速度。它走的是另一条路：CLI 还在 Node 里，核心在 Rust，插件和 webpack 的心智模型可以接着用。

如果现有项目已经绑在 Parcel 2 的插件、磁盘缓存和 scope hoisting 上，现在不必为了那句「100 倍」迁到 alpha。Parcel 2 在这份中型应用上只需大约 1.6 秒，慢是相对的；它换来的是更成熟的 Node 插件生态，以及更小的 JS 产物。等 Parcel 3 把公告里那些缺口补上，再看体积策略会不会往回调，会更从容。

我不会再追 100× 这个数字。它写在 React Spectrum 那种规模的冷开发构建上，换到 390 个模块的生产构建，倍数掉下来更像缩放规律，而不是实现没达标。更值得看的是这次重写选了什么、丢掉了什么：一条不再经过 Node 的原生管线，换来的是冷构建和内存，付出去的是插件生态、scope hoisting，以及 alpha 阶段还没补齐的那些能力。
