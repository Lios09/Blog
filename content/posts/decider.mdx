## 1. 生成模型先让工单分类跑起来，但任务本身是一道选择题

[Amazon saves millions by replacing Sonnet 4.6 with Strands Decider](https://strandsagents.com/blog/amazon-saves-millions-replacing-sonnet-with-strands-decider/)发布于 2026-11-09，作者是 Carr Onstott、Mehul Jaiswal 和 Strands Agents Team。文章写的是 Amazon 内部一套规模极大的工单系统：在一段时间里，Amazon 和 AWS 的团队用 Claude Sonnet 4.6 给工单打标签，既要够聪明，又不能把账单打爆。作者把当时的选择写成 goldilocks——在智力和成本之间刚刚好。考虑到这是「one of the world's largest internal ticketing systems」，他们也承认，这个已经用了九个月的模型表现不错。

后来他们把它换成了大约一个月前发布的 Strands Decider。官方的概括是：新模型「performed just as well at 98% less cost」，「This change will save millions of dollars of token costs in a year。」这两句都是他们自己的结论和测算，下文会拆开看数字从哪里来；我没有复现这套生产流量。

工单本身可以是客户升级、容量申请、自动告警、安全发现，以及公司里任何需要归进大约 20 个类别的东西。旧路径是一个 agent：每张工单都带着很长的 system prompt，对着固定的标签集合生成 JSON，并写出推理过程。换句话说，生产线上真正要的是「从已知目录里选一个标签」，可接口却是「请写一段带推理的结构化文本」。生成能力在这里是手段，不是任务本身的要求。

决策模型正好站在另一侧。它不能生成文本。调用方先给出一些状态（state）、一个问题和一组选项，模型返回每个选项的概率，外加一个置信度。作者立刻对上了工单打标：状态是工单，选项是标签目录。任务接口一旦从「写一段话」收成「在给定选项里打分」，后面的延迟、费用、校准和回滚，才会沿着另一条设计往下走。

他们先试了最初的 Strands Decider 2B。在自己的工单测试集上，E4B 的 Gemma 4 构建明显更好，于是换了过去；接着调节模型要多有把握才肯打上标签。结果是：在另一份单独的工单集合上，E4B 超过了生产环境里的 Sonnet。文章没有公布这份对比的准确率百分比，所以我也不去补一个。

![工单事件进入 SQS，由 Lambda 读取；先对 JSON 键排序，过长则丢掉最旧的评论；再把工单作为状态、把二十条一两句判据加上 none 作为选项送给 Decider；模型返回每个选项的概率和置信度，达到阈值且不是 none 就应用标签，否则升级](/posts/decider/request-flow.svg)

## 2. 决策模型到底输出什么

要理解这次替换为什么成立，得先把「决策模型」从营销词还原成一种接口。2026-10-01 的介绍文 [Introducing Strands Decider 2B](https://strandsagents.com/blog/introducing-strands-decider/) 把它写成一类新出现的 decision model，或 system one model。作者 Marc Brooker、Mike Chambers 和 Fabio Nonato de Paula 写：这类模型从 TypeSafe AI 当月早些时候发布的 Jev 开始，受到很多关注。和可以生成任意文本的 LLM 不同，决策模型被设计来在一组选项里做选择，并给出简单的数值分数。介绍文举的例子包括：一句话是不是在说咖啡机，一段话是英语、祖鲁语还是荷兰语，以及一句评论的情感在 0 到 1 之间打分。

它拿灵活性换了三样东西：同样参数量下更快、也更擅长做决定；答案一定落在你提供的选项里；延迟可以非常低。代价也写得很清楚：所有输出在一次并行的前向里同时产生，这让它在复杂问题上明显弱于推理模型；又因为不能生成文本，它不适合编码、聊天、摘要，以及其它常见的 LLM 任务。作为补偿，它会给每个决定一个高质量的可靠性分数——介绍文的原话是，这种分数「is not available through frontier LLM inference APIs」。对同一段 prompt 问多个问题，也因此变得很便宜。

模型结构比这句产品描述更具体。[架构文档](https://strandsagents.com/docs/labs/strands-decider/architecture/)写的是：取一个预训练好的解码器 LLM 躯干，丢掉它的语言模型头（language-modelling head），也就是去掉生成文本的能力；再换上一个大约一百万参数的 pointer head。躯干用 rank-16 的 LoRA 适配。一次请求会被渲染成单一 prompt，结构是 `<state>…</state>`、带类型的 `<question>`（里面再嵌 `<options>`），最后停在 `<answer>`。躯干只跑一遍。pointer head 把 `<answer>` 位置的隐状态当作 query，把每个选项那一行最后一个 token 的隐状态当作 key——在因果注意力下，这个 token 刚好读完了自己那一行——然后打分：

`logit_k = <q(h_answer), k(h_option_k)> / sqrt(dim)`

对这些 logit 做 softmax，就是答案。整条推理路径到此结束：一次前向，没有生成，也没有解码循环。介绍文里的 2B 用的躯干是 Qwen3.5-2B；架构文档把 v13 到 v19 写成 Qwen3.5-2B-Base。读出头本身很小，只有大约一百万参数（`dim=256`），并且用 fp32 计算——架构文档解释说，躯干可以跑 bf16，但一个低精度的分类头会平白制造校准误差。

三种问题类型是同一种带掩码的 softmax，读法不同：

- `noul`：二选一的是否题，返回 `P(true)`。
- `choice`：N 选一，返回 argmax、每个选项的概率，以及置信度。
- `score`：在 2 到 10 个有序等级上打分，返回期望值、分布和置信度。

工单打标走的是 `choice`。介绍文里的命令行例子把这一点写得很直白：`--state` 放客户留言，`--choice "Which team should handle this?=billing,sales,retail"`，模型打印出选中的项、一个置信度，以及 billing / retail / sales 各自的概率。Amazon 的用法只是把「该由哪个团队处理」换成「该打哪个标签」，把选项从三个部门名换成二十条判据。

有一个细节会改变你怎么用这些数字：**choice 的置信度不是另训出来的，而是从概率推导的。** 架构文档给出的公式是：

`confidence = (N · p_max − 1) / (N − 1)`

均匀分布时为 0，one-hot 时为 1，而且和 N 无关。于是同一个路由阈值，在 3 个选项和 10 个选项的问题上表示的是同一种「有把握的程度」。`noul` 没有单独的置信度字段，因为只有两个结果时，概率本身就是不确定度。Amazon 后来「tuned how confident the model needed to be before applying a label」，调的就是这类可以比较的分数，而不是让生成模型在 JSON 里再写一句「我很确定」。

pointer head 还有一个和分类器很不一样的后果：选项的分数取决于它写了什么，而不是它排在第几位。模型里没有按选项编号准备的参数，因此它学不会「第一个选项通常是对的」，选项数量也不被权重结构封顶——架构文档说，上限只来自 schema 的 255。同一套权重可以回答两选项的是否题，也可以做三十选项的路由；训练时没见过的标签集合，只要请求里写清楚每个选项是什么意思，就可以拿来用。作者把这写成 runtime-defined labels：增加一个类别不必重新训练。训练时还有一条比任何损失函数都重要的规则：每个样本、每个 epoch 都会重排选项顺序，标签跟着一起映射；否则读出头会默默记住「槽位 0 常常是正类」，所谓的通用性就没了。

所以，决策模型不是「一个不肯说话的小聊天模型」。它改变的是计算图：生成头被拿掉，选项在请求里被读成文本，答案是一次 softmax。Amazon 拿它替换 Sonnet，不是因为 2B 或 E4B 突然学会了写更好的工单摘要，而是因为打标从来就不需要那段摘要。

## 3. 把二十个标签写成一两句判据

官方把 token 下降写成两个来源。第一，Strands Decider 只产出一个输出，也就是那个选择，而不再写一份 JSON 答案：每张工单的输出 token 从 170 降到 1。第二，它的 prompt 也比 Sonnet 4.6 短得多。生产环境里，光是标签描述就已经长过 Strands Decider 的 4,096 token 窗口，所以他们把 20 个标签各自改写成一两句判据（one- or two-sentence criterion），作为一道选择题的选项送进去，并加上一个 none。工单数据和 Sonnet 拿到的相同，唯一的例外是：遇到过长的工单，Strands Decider 会丢掉最旧的评论，好让内容塞进窗口。

这不是在「压缩一下 prompt 试试」。旧的标签说明既然已经超过窗口，决策模型这条路在物理上就走不通，除非先改写目录。而 pointer head 读的正是选项文本——选项写得越像一条可判定的标准，模型要匹配的对象就越清楚。下面这组对比是我写的示意，用来说明「名字」和「判据」差在哪里，不是他们的标签目录：

- 只给名字：`networking`
- 写成判据：工单描述的是网络连通性、VPN、证书轮换或防火墙变更，而不是应用代码缺陷或权限开通。

加上 none，等于在目录里显式留下「这些标准都不适用」。后面的弃权和升级，有一半是从这里开始的：模型不仅可以给出低置信度，还可以把概率砸在 none 上。

他们公布的调用侧数字如下。平均每次调用从 4,215 毫秒降到 897 毫秒，改善 78%；每张工单的输入 token 从 6,554 降到 2,009，输出 token 从 170 降到 1，合计从 6,724 降到 2,010，少了 70%。这些都是官方自己的测量。文章还附了一张图：关掉 Sonnet 的那天，Lambda 的平均执行时间下降了 74%。注意两套时间不是一回事——他们另写：模型在单台实例上一次请求大约 640 毫秒；897 毫秒是平均每次调用，4,215 毫秒则是旧路径上的同口径数字。

费用按 us-east-1 的公开按需标价计算。Claude Sonnet 4.6 走 Bedrock 的 global endpoint，每百万输入 token 3.00 美元，每百万输出 token 15.00 美元，折合每张工单 0.0222 美元，每一百万张大约 22,200 美元。Strands Decider E4B 跑在 SageMaker 的 `ml.g5.xlarge` 上，每实例小时 1.408 美元。一次请求大约 640 毫秒，一台实例满载大约能处理 5,600 张工单，满载时每一百万张大约 250 美元；他们会留突发余量，实际大约是每一百万张 500 美元，也就是每张大约 0.0005 美元。官方把它写成大约便宜 44 倍，降幅 98%。这些是公开标价，还没有计入 Lambda——而 Lambda 现在每张工单也跑得更短。

服务形态写得很具体。E4B 跑在 `ml.g5.xlarge` 上（一张 A10G，24 GB），模型大约占用 19 GiB，单实例一次请求大约 640 毫秒。端点会随流量自动扩缩，但网络是隔离的，容器不能出站；SageMaker 在启动前从 S3 拷入权重。工单事件进入 SQS，触发 Lambda，Lambda 读出工单再调用这个 SageMaker 端点。开关放在 AppConfig 里，日志、指标和告警走 CloudWatch，整套栈用 CDK 定义，并分成 Beta、Gamma、Prod 几个部署阶段。作者强调：除了他们的工单 API，路径上其余都是标准 AWS 服务。

2B 和 E4B 分别是什么，需要按出处分开写。2026-10-01 的介绍文把 Strands Decider 2B 写成一个 20 亿参数、可在本地 CPU 或 GPU 上跑的开源模型，代码在 GitHub，权重建在 Hugging Face，训练数据和脚本一并发布；它针对快速试验、本地开发和继续创新。Amazon 的案例里，他们先用「the original Strands Decider 2B」，再因为自己的测试集而换成「the E4B Gemma 4 build」。2026-10-15，Strands 又发布了基于 Gemma 4 的四个尺寸：E2B、E4B、12B 和 26B-A4B，公开的 E4B 标识是 `StrandsAgents/strands-decider-E4B-gemma4-v1-2610`。案例没有写出生产环境用的就是这个 Hugging Face 标识，所以我只把它当作后来公开的同名构建，不去断言两边字节级一致。Gemma 4 那一组模型保留了同一套问题类型，以及 LoRA 加 pointer head 的结构。

## 4. 校准、阈值，以及「不够确信就不要自动打标」

生成式路径给你的是一段文本。即使你要求它输出 JSON，里面那个 `"confidence": "high"` 也只是又一段被采样出来的词，不是可以对着频率去验收的分数。介绍文把决策模型的可靠性分数，特地拿来和前沿 LLM 推理 API 做对比：后者通常不提供这种东西。于是旧路径上想做「没有把握就不要自动打标」，往往得求助于另一套启发式——看模型有没有输出某个标签名、输出是否能解析、或者再问模型一次它有多确定。

决策模型把这件事收成两个可以直接写进规则的量。一是每个选项的概率，二是由最大概率归一化得到的置信度。因为公式对 N 做了归一，20 个标签加一个 none 时的 0.8，和三个团队里选一个时的 0.8，表示的是同一种「远离均匀分布」的程度。Amazon 的工程师做的下一件事，不是继续改 prompt，而是调节「要多有把握才打上标签」。

具体怎么用，文章没有给出他们的阈值。架构文档借用了公开 Jev API 文档里的示例分档：0.9 及以上可以直接执行，0.5 到 0.9 先确认，低于 0.5 交给人；同时又写明，合适的阈值取决于每一种动作的后果，必须在自己的流量上测量。这些分档不是 Amazon 工单系统公布的数字，我不把它们写成生产配置。对工单打标来说，更重要的是形状：

- 最高概率项不是 none，且置信度达到阈值：应用这个标签，按类路由。
- 模型选了 none，或置信度不够：不要自动打标，升级给人，或走原来的保底路径。

none 和低置信度不是一回事。前者说的是「这些判据我都不认可」，后者说的是「即使最像的那一条，也没有远离其它选项」。两个出口都指向弃权，但修法不同：经常落到 none，可能是目录没覆盖真实业务；经常低置信，可能是判据写得重叠，或工单信息不够。校准要回答的问题是：当模型报出 0.8 时，它是不是大约在 80% 的时候是对的。介绍文把校准和准确率放在一起衡量，用的是 JevBench 公开集上的 Brier score。Amazon 的案例没有公布工单任务上的可靠性图，只说他们调节了打标所需的把握程度，并且 E4B 在单独的工单集合上超过了生产环境里的 Sonnet。

这改变的不只是指标，还有产品允许你做什么。有了可比较的置信度，覆盖率和精确率可以变成一个旋钮：阈值升高，自动打标变少，但留下来的更干净；阈值降低，自动化变多，升级队列变短。生成模型当然也能「拒绝回答」，可拒绝本身仍是一段文本，既不好设阈值，也不好在周与周之间比较。决策模型把弃权从文风问题收成了策略问题。

架构文档还解释了他们为什么把读出头放在 fp32：头很小，一个低精度分类头会平白制造校准误差。对「输出要拿来设阈值」的模型，这件事和准确率同样重要。一个看起来很自信、实际上经常在 0.7 附近说错的分数，比一个略低但靠谱的分数更危险，因为它会让你把阈值设错。

## 5. 三档开关：BEDROCK、DUAL、DECIDER

他们不想「翻转一个开关然后祈望没事」。打标的 Lambda 每条消息都会从 AWS AppConfig 读取一个三档设置：

- `BEDROCK`：每张工单都由 Sonnet 打标，不调用 Strands Decider。
- `DUAL`：Sonnet 和 Strands Decider 并行调用。采用 Sonnet 的结果打到工单上，同时和 Strands Decider 的结果做比较。
- `DECIDER`：每张工单都由 Strands Decider 打标，不再调用 Bedrock。

![Lambda 每条消息从 AppConfig 读取三档开关：BEDROCK 只让 Sonnet 打标；DUAL 并行调用两者，采用 Sonnet 的结果，同时比较 Decider 并审阅分歧；DECIDER 只让 Decider 打标。从 DECIDER 改回 BEDROCK 是一次约 45 秒的配置变更](/posts/decider/rollout-switch.svg)

DUAL 的关键不在「两个模型都跑一下」，而在写回工单的仍然是旧路径。新模型在真实流量上留下影子，生产行为暂时不变。作者写道：在真实流量上同时跑两者，再判断每一处分歧，比任何离线评估告诉他们的都多。这也意味着退回去只是一次大约 45 秒的配置变更。

我愿意把这套开关看成和模型本身同级的设计。离线测试集再用心，也很难覆盖告警风暴、罕见安全发现、或某一类工单在某周突然变长之类的事情。DUAL 把评估从「我们准备好的那份样本」挪到「现在正在进系统的工单」，代价是在这一档里你要付两次推理的钱——一次 Sonnet，一次 Decider。等分歧被审过、阈值被调过，再切到 `DECIDER`，延迟和费用才会落到他们公布的那一组数字上。如果新模型在某一类工单上开始胡闹，切回 `BEDROCK` 不需要重新部署 Lambda，也不需要等 SageMaker 端点冷启动一套旧模型。

作者在文末把这句话写给所有人：不论用什么模型，这部分他们都会照抄。我同意。专用于决策的模型可以换，三档开关描述的是一种更通用的上线纪律：新路径先做影子，写回仍走旧路径，回滚是配置而不是发布。

## 6. JSON 键顺序最多能让概率偏 0.19

案例里有一段他们自己也感到意外的观察：JSON 的键顺序会改变答案。同一份内容，只是键的排列不同，输出概率最多能移动 0.19。他们现在会把每个请求的键排序后再发送，并提醒：如果你在 API 后面提供决策模型，比较两次运行之前先检查这件事。

0.19 不是一个可以忽略的抖动。对一道多选项的分类题，它足以把「勉强领先」变成「看起来很有把握」，或把两个接近的标签调换名次。若你正在 DUAL 档里统计分歧，不稳定的序列化会让你以为模型在翻来覆去，其实是同一张工单被写成了两种字符串。

架构文档里还有另一组相关、但不能混为一谈的数字：把选项列表整段颠倒，分布大约只移动 0.016。作者把它归因于因果注意力下，后面的选项仍然能看到前面的选项；若要彻底消除，需要对每个选项做注意力隔离，而他们没有实现这一点。0.016 和 0.19 差了一个数量级，对象也不一样——前者是选项顺序，后者是状态（工单）被序列化成 JSON 时的键顺序。训练时每个样本都会重排选项，模型被明确地正则化过，不要去背「第几个槽位更常是对的」；没有人用同样的力度，去正则化 JSON 字段谁先谁后。

至于键顺序为什么能动得这么厉害，官方没有给出机制上的解释。下面是我的推测。决策模型仍然是因果序列模型：整条隐状态轨迹都依赖于 token 的先后。工单状态可以占到提示的很大一块，键一换顺序，就等于改写了一大段前缀；`<answer>` 处的 query，以及每个选项末 token 处的 key，都已经读过这段被打乱的前缀。分词也会跟着变：`"priority"` 和 `"title"` 谁先出现，会改变引号、逗号、冒号附近的 token 切分。再往后看位置——在因果注意力下，更靠近问题和选项的字段，对后续隐状态的影响往往更大，于是把标题从对象的第一个键挪到最后一个键，并不是一次很小的扰动。这些都是对「序列模型会对表面形式敏感」的合理引申，不是他们测量 0.19 时给出的原因。

下面这段示意代码演示的是请求出厂前的规范化，不是打分本身。我用 Python 3.13.5 跑过，输出是这次实际打印的结果。它不是 Amazon 或 Strands 的源码。

```python
# 非官方实现 / 示意：送给决策模型之前，把状态 JSON 的键排序。
import json


def canonicalize(obj):
    if isinstance(obj, dict):
        return {k: canonicalize(obj[k]) for k in sorted(obj)}
    if isinstance(obj, list):
        return [canonicalize(x) for x in obj]
    return obj


ticket_a = {
    "priority": "high",
    "title": "VPN cannot connect after the certificate rotation",
    "queue": "network",
}
ticket_b = {
    "queue": "network",
    "title": "VPN cannot connect after the certificate rotation",
    "priority": "high",
}

raw_a = json.dumps(ticket_a, ensure_ascii=False)
raw_b = json.dumps(ticket_b, ensure_ascii=False)
canon_a = json.dumps(canonicalize(ticket_a), ensure_ascii=False)
canon_b = json.dumps(canonicalize(ticket_b), ensure_ascii=False)

print("unsorted equal:", raw_a == raw_b)
print("raw_a:", raw_a)
print("raw_b:", raw_b)
print("canonical equal:", canon_a == canon_b)
print("canonical:", canon_a)
```

```text
unsorted equal: False
raw_a: {"priority": "high", "title": "VPN cannot connect after the certificate rotation", "queue": "network"}
raw_b: {"queue": "network", "title": "VPN cannot connect after the certificate rotation", "priority": "high"}
canonical equal: True
canonical: {"priority": "high", "queue": "network", "title": "VPN cannot connect after the certificate rotation"}
```

两份对象在键值上完全一样，默认的 `json.dumps` 却会按照插入顺序写出两种字符串。排过序之后，它们变成同一条输入。决策模型若对这种差异敏感，API 边界就应该先做这件事，再去谈两次运行是否可复现，或 DUAL 里的某次分歧是不是真分歧。

## 7. 和另外三种做法比，各自适合什么

把生成模型换成决策模型，并不是分类问题上唯一的路，也未必总是最合适的那一条。至少还有三种常见做法，和它抢的是同一类任务。

经典的微调分类器，比如线性模型、SVM，或 BERT 一类编码器加上固定类别的分类头，仍然是延迟和费用的下限。Hacker News 上有人提起六年前用 SVM 做工单和日志分类的 [Linnaeus](https://arxiv.org/abs/2103.06927)：训练只要几分钟，推断是毫秒级。这条路要求你已经有带标签的历史，并且类别相对稳定——标签写在最后一层的权重里，目录一改，通常就要补数据、再训练。它适合目录稳定、历史标签充足、也愿意维护一条训练和评估回路的团队。它不适合你手头只有一段文字政策、下星期就要上线，或类别每个迭代都在改写法的阶段。决策模型把标签留在请求里，新增一类不必重训；经典分类器用更低的单次成本，换来的是「类别是模型的一部分」。

用生成式 LLM 做基于 logprob 的分类，是一条看起来很近的中间路：你让模型在 A / B / C 或若干标签名里选一个，然后读取这些 token 的对数概率，当成伪分布。它仍然是生成模型。标签名往往会被切成多个 token，API 也不一定暴露 logprob；你得到的是词表上的质量，不一定是「选项文本被读懂之后」的质量。提示的措辞、选项的排列，同样会打动它。量不大、你已经在调用某个 LLM、只是想给输出加一点结构时，这条路很方便。Amazon 的旧路径比这更重：模型不仅要选出标签，还要生成带推理的 JSON，每张工单 170 个输出 token。决策模型把「在选项上做 softmax」从一种提示技巧，做成了模型头上的计算。

向量嵌入加上 kNN（或类似的近邻投票）适合另一种判断：「这张工单像不像以前那张」。新工单被做成向量，在已标注的历史里找邻居，用邻居的标签来投票；距离太大就拒识。当正确答案确实是「和某类历史工单相似」时，这条路干净而且便宜。当正确答案来自一条书面标准——例如「只有涉及证书轮换才算网络类」，而最近邻里恰好堆着许多看起来像网络、其实是权限开通的旧单——相似度就会把你带偏。给目录增加一个新类，你需要的是一批例子，而不是一句判据。距离阈值也可以拿来弃权，但它校准的是向量空间里的远近，不是一组口头定义过的选项上的概率。

决策模型站在这些做法中间的某处。它保留了「用自然语言描述类别」的零样本味道，又把输出收成一次可设阈值的分布；选项在请求里定义，目录变动不必重训；一次前向，没有解码循环。Amazon 自己给出的适用条件是：任务是从已知目录里做封闭选择，量很大，而且旧路径的延迟已经构成问题。他们同样写出了不适用的情况：标签还需要解释文本；目录每周都在变；或者有用的上下文塞不进几千个 token。

最后这一句值得多想一下。按架构，标签本来就是运行时定义的，按理说改目录并不需要重训。我的理解是：每周都改目录，改的不只是选项字符串，还有判据怎么写、阈值要不要重调、DUAL 里新出现的分歧怎么审。决策模型又不能生成解释，新类一模糊，你很难像追问 Sonnet 那样让它说出自己为什么这样分。上下文塞不进窗口时，他们的做法是丢掉最旧的评论——这是明确的信息损失，尤其当一张工单的关键说明写在较早的回复里，而不在最后几条时。这些限制都不是我对模型的猜测，而是他们对自己适用边界的说明；「每周改目录为何仍然麻烦」这一层，是我的引申。

## 8. 我的看法

1. **真正被换掉的是接口，不是换了一个更小的聊天模型。** 如果只是把 Sonnet 换成某个更便宜的生成模型，你仍然在为「写一段 JSON 和一段推理」付输出 token，仍然拿不到一个可以和频率对上的置信度，也仍然无法从结构上保证答案落在目录里。Amazon 做对的第一步，是承认打标是一道封闭选择题。pointer head、一次前向、runtime-defined labels，都是在为这个接口服务。98% 的费用下降里，有一部分来自更小的模型和自建推理，有一部分来自输出从 170 个 token 变成 1 个，还有一部分来自把超过窗口的标签说明改写成二十条判据。把这些混成「小模型就是便宜」，会看丢最值得学的那一层。

2. **把标签改写成一两句判据，既是在压缩 prompt，也是在重新规定分类标准。** 生产环境的旧描述长过 4,096 token，不改写就无法使用决策模型，这是硬约束。改写之后，模型匹配的对象从「请你理解我们内部那套冗长说明」变成「请你阅读这条可判定的句子」。pointer head 读的是选项文本，判据写得越清楚，分数就越像在做标准匹配，而不是在联想一个标签名。none 则迫使目录承认自己覆盖不全。我没有看到他们的二十条原文，所以不能评价改写质量；但就设计而言，这一步和换模型同样关键。

3. **三档开关比模型本身更值得照抄。** `BEDROCK` / `DUAL` / `DECIDER` 把上线拆成「旧路径保证正确写回」「新路径在真实流量上暴露分歧」「确认后再切过去」，回滚是大约 45 秒的配置变更。作者自己也说，不论用什么模型，这部分他们都会留下。离线测试集回答的是「在我们准备好的样本上谁更好」；DUAL 回答的是「这周实际进系统的工单上，两人在哪里吵起来」。对于会随时间漂移的内部工单，后者更接近生产。

4. **校准过的置信度，加上可以选 none，才让自动打标敢于离开人工兜底。** 生成模型并非不能拒答，但它的拒答是文本，阈值是启发式。决策模型把「有多有把握」收成一个和 N 无关的数字，于是覆盖率和精确率可以变成策略。调这个阈值，是他们在换模型之后立刻做的事。官方没有公布工单任务上的可靠性图，也没有写出具体阈值；我愿意把「先有分数、再设阈值、分歧拿来人工看」当成可迁移的做法，而不是去猜那个数字是 0.7 还是 0.9。

5. **JSON 键顺序提醒你：这些模型对表面形式仍然敏感，请求边界必须先规范化。** 最多 0.19 的概率偏移，足够污染 DUAL 里的分歧统计，也足够让两次「相同」的评估失去可比性。选项顺序在训练里被刻意打乱，状态字段的顺序没有得到同等待遇，这或许有助于理解为什么官方对选项颠倒只测到约 0.016，对 JSON 键顺序却看到 0.19——后面这半句是我的推测。可执行的结论倒不依赖推测：在 API 入口把键排好序，再去谈复现和对比。

6. **官方的延迟、token 和费用数字，应当当作他们的自测来引用。** 4,215 毫秒到 897 毫秒、6,724 到 2,010 个 token、约 98% 的费用下降、满载约 250 美元/百万张与留余量后约 500 美元/百万张，以及「一年将节省数百万美元」，都来自那篇案例。费用还明确取决于实例有多忙。我没有在生产流量上复现这些数字，也没有跑过 E4B 或 Sonnet 4.6 的对照。对设计更有用的，是他们写下的适用边界：封闭选择、目录已知、量大、旧路径的延迟已经是问题；需要解释文本、目录每周都变、或上下文塞不进几千 token 时，决策模型大概替换不了 LLM 的工作。丢掉最旧评论去迁就窗口，是这条边界里已经被接受的信息损失，不是附赠的免费优化。
