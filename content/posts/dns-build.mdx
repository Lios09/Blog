## 1. 全量构建最简单，也最先跟不上区的规模

[How we halved DNS build delay and cut memory use by 85%](https://blog.cloudflare.com/dns-targeted-zone-builds/)发布于 2026-11-02，作者是 Alex Fattouche。它接的是同一作者 2022-05-25 的[另一篇](https://blog.cloudflare.com/dns-build-improvement/)：那时 Zone Builder 已经把「改一条 DNS 记录」从全量重建改成了 per-record build。2022 年的数字是：Zone Builder 大约每秒收到 250 条记录变更；per-record 构建平均比全量快 150 倍；在一个百万条记录的测试区上，快 4,250 倍（单条 6 到 8 毫秒，全量大约 34 秒）。那篇文章结尾说，下一步显然是对区域设置做同样的事，并计划引入一套批处理，减少对数据库和 Quicksilver 的查询次数。

四年后，2026 年的文章写：Zone Builder 大约每秒收到 700 条记录变更，接近当时的三倍，另外大约还有 100 个其他事件，比如区域设置变更。但作者立刻把主语从「事件有多少」拧到「事件要做多少活」：有的区现在已经超过两千万条记录，而且他们预期会继续涨到数亿条。事件数量从来不是真正的问题；真正的问题是，某些事件所需的工作量会跟着区的规模一起涨。

一次构建（build）的定义写得很清楚：读取当前数据库状态，转成边缘使用的格式，再把任何变化写入 [Quicksilver](https://blog.cloudflare.com/introducing-quicksilver-configuration-distribution-at-internet-scale/)。2020-03-30 的介绍文把 Quicksilver 写成 Cloudflare 自研的、用 LMDB 做存储、按 fan-out 把配置复制到各数据中心的分布式键值存储；2026 年这篇则把它称作「our distributed key-value store」，权威 DNS 服务器从这里读取答案。构建完成延迟统计到「Zone Builder 写完 Quicksilver」为止，不包括随后在网络各处的分发时间——作者明确说，那一部分随地点变化，而且不受这次改动影响。

原始 Zone Builder 有一个非常有用的性质：它不需要知道区为什么变了。它只从当前数据库状态重建期望状态：

1. 读取当前区和它的设置；
2. 读取区里的每一条 DNS 记录；
3. 把这些记录转成 Quicksilver key；
4. 和已经存在的 key 做比较；
5. 删掉过期的，写下变化的，更新区的元数据。

最后一次写入确实只包含变化的 key。可是一次全量构建仍然要读取、编码并比较每一条记录，并且在此期间把整个区放进内存。小区很便宜；对「有数千万条记录」的最大区来说，区已经无法完整放进内存。作者后文会解释他们怎么处理这种区，但代价很清楚：正确性来自「每次都从真相源重算」，性能则和区的大小绑在一起。

区域设置让「只重建改过的那部分」更难。文章举的例子是 Universal SSL：打开或关闭它会更新元数据，还可能改写区顶点（apex，也就是 `example.com` 这种裸域名）上的 CAA 记录。CAA 用来告诉证书颁发机构是否可以为这个域签发证书。记录事件通常能指出改了哪一条；区域事件却可能来自许多 Cloudflare 产品，不一定说明区为什么变了，还可能改动「同名的多个区」共享的那份数据。选多了浪费容量，选少了会在边缘留下过期或不正确的 DNS 数据。

所以这次工作的主语不是「再快一点」，而是「证明什么时候少干活仍然正确」。作者把它拆成五个必须先解决的问题：事件得说出改了什么；每种改动得映射到仍然正确的最小构建；构建必须考虑同名各区共享的数据；事件和真正开建之间数据库可能又变了；合并工作不能丢掉一条 Kafka 消息。

![DNS 变更经数据库和 Kafka，由 DNS Kafka Aggregator 合并后进入 Zone Builder；规划器选择可证明安全的最小构建，执行前用新鲜快照再规划，统一调度器做加法合并，再把变化的 key 写入 Quicksilver](/posts/dns-build/pipeline.svg)

管道本身并没有换一套新系统。客户通过 DNS Records API 或控制台改一条记录，或其他 Cloudflare 服务改一项区域设置；变更写入数据库；数据库变更或其他系统产生 Kafka 事件；DNS Kafka Aggregator 合并多个 topic，再送给 Zone Builder；Zone Builder 读出所需的区数据，转成权威服务器能理解的 key，和 Quicksilver 里已有的比较，只写变化的部分。作者强调这是简化视图：Zone Builder 并不是把数据库行直接拷到边缘，它会把记录和区域设置合在一起，套上 DNS 服务规则，再把结果组织成权威服务器能快速读取的形状。

## 2. 五种构建，以及「字节级一致否则退回全量」

要少干活，事件就得先变得更具体。他们改了事件生产者，让它带上变化的区域字段和设置，并在能够拿到时附上旧值和新值；接着沿着生成 DNS 输出的代码，追溯每项设置可能影响什么，再给它分类。

不是每一种事件都能这么具体。有些数据库函数只更新一个时间戳，相当于说「这个区有什么东西变了」。有时这只是无害的簿记，有时却意味着数据在别处改过、必须重新读一遍。这两种情况在事件上看起来一模一样。在能够识别调用方和意图之前，只改了时间戳的更新仍然会触发全量构建。同样的规则也适用于缺失细节、未知事件，或任何可能影响区里任意记录的变更。作者把规划器的性格写成一句原则：**The planner never turns uncertainty into less work.** 不确定，就不要把它翻译成更少的工作。

Quicksilver 的输出在这里有两部分。记录 key 保存一个区、一个名字下的 DNS 答案；另有一个较小的共享元数据 key，告诉权威服务器怎么使用这个区，包括去哪里找 nameserver、通配符这类特殊记录。有的事件只改记录 key，有的必须两边一起更新。有了这个区分，规划器就可以在五种构建里选一种：

| 构建类型               | 做什么                                                         | 典型触发                                    |
| ---------------------- | -------------------------------------------------------------- | ------------------------------------------- |
| Resources only         | 重建指定 DNS 名字（他们称为 resource）上的记录，不改区域元数据 | 普通的 A、AAAA、TXT、CNAME 变更通常走这条路 |
| Resources and metadata | 重建指定名字，并更新共享元数据                                 | nameserver 和通配符变更                     |
| Apex and metadata      | 重建区顶点与元数据                                             | Universal SSL 这类设置可以走这条路          |
| Purge                  | 移除一个不应再被发布的区                                       | 区对当前网络不再发布                        |
| Full zone              | 重建每一条记录                                                 | 更小的工作无法被证明安全时                  |

规则本身很简单，也是整篇文章最值得记住的一句：定向构建写出的每个 key，都必须和一次全量构建写出的结果字节级一致；如果不能证明这一点，就做全量构建。

清理旧状态的方式和 2022 年的 per-record 构建相同。记录事件会带上已删除的记录，以及被更新记录的旧版本；Zone Builder 再扫描它即将重建的每个名字下、Quicksilver 里已有的 key，删掉新构建没有写出的那些。2022 年他们就吃过这个亏：当时 PGQ 产生的更新事件只包含新记录，记录改名之后，旧名字无法从 Quicksilver 里清掉，后来是靠把这类更新拆成一条创建加一条删除才补上信息。定向构建能成立，依赖的不只是「少读几条记录」，还依赖事件里带着足够的「以前是什么」。

全量构建仍然必要。一种情况是变更可能影响区里任何地方的记录；另一种是一个区可能需要第一次被发布，必须把每条记录都写出去。对小区来说，全量构建本身也并不贵。

还有一个刻意留下的例外。一次全量构建会同时把数据库里的全部记录和 Quicksilver 里该区已有的全部 key 放进内存，而最大的那些区放不下。超过一个固定的记录数阈值之后，Zone Builder 不再升级到全量构建，而是重建顶点、元数据，以及排队事件里指出的每一个名字。作者接受这个取舍，因为对这些区做全量构建根本完成不了，重试期间还会拖住同一 Kafka 分区上别人的变更。许多「本该全量」的情形来自多个区共享一个名字，而 zone hold 通过阻止同一个名字被加到另一个账户，降低了这种风险。剩下的罕见情形，比如在另一个网络上启用一个区，他们可以手工重建区里的个别名字。文章没有写出这个记录数阈值是多少，所以我也不去猜。

## 3. 同名多区、两次规划，以及只做加法的统一调度器

Quicksilver 把每个区的记录 key 分开存，但又为每一个公开域名准备了一份所有 Cloudflare 区共享的元数据 key。这份 key 像目录：它告诉权威服务器，回答查询时可以使用哪些内部区 ID。

为什么一个名字会对应多个区 ID？在客户开通、关闭和其他生命周期变化中，同一个公开域名下可能短暂存在多个 Cloudflare 区对象。他们用一套优先级策略，从中选出一个小而有界的集合来发布。文章举的例子是 `example.com` 下的四个内部区：Zone 101、202、303、404。元数据 key 当前列出 101、202、303；404 存在，但没有被选中。客户仍然只看见一个域名。

在 Zone 202 的 `www.example.com` 上改一条 TXT，只影响 Zone 202 自己的记录 key，元数据 key 不用动。nameserver 和通配符就不同了，因为元数据 key 里记录了和它们有关的信息，这类构建必须同时更新该区的记录和这份共享 key。

执行时，Zone Builder 会再读一遍当前列表。如果它要写元数据 key，就会按这份新鲜视图重建整把 key，而不是在旧副本上打补丁。写入顺序也有规定：先写触发这次构建的那个区的记录，再写引用这些记录的元数据。作者没有展开这个顺序的理由；按这两类 key 的含义来理解，如果目录先指向还没写好的记录，中间会短暂不一致。

事件描述的是过去发生的事。构建可能还要等更多事件进来，数据库也可能已经又变了，所以规划会发生两次。事件先生成一份保守的工作清单；即将执行时，Zone Builder 再读取一份新鲜的发布快照：当前的区域设置、这个 Zone Builder 是否应当把该区发布到它对应的网络，以及哪些同名区 ID 应当出现在元数据 key 里。这里的「网络」是 Quicksilver 的一份隔离副本，对应一个环境；每个 Zone Builder 部署只写其中一个网络，而一个区可以在某些网络上启用、在另一些上不启用。作者举的例子是：一个区既可以在 Cloudflare 的全球网络上服务，也可以同时出现在 China Network 上。

新鲜状态会以四种方式改写结果：

1. 如果这个区现在具备了需要整区工作的特性，定向构建可以升级成全量构建；
2. 如果这个区不应再发布到当前网络，构建可以变成 purge；
3. 如果触发构建的那个区已经不再属于元数据 key，这次构建可以直接跳过；
4. 一次元数据构建可以按当前候选集合重建共享 key。

新鲜读取来自数据库的只读副本（replica），以免构建和客户写入互相抢。Kafka 投递和数据库复制是独立前进的：事件可能在副本上看不见对应的库变更之前就到达。DNS Kafka Aggregator 会把事件延迟到足以覆盖正常滞后的程度，最后还有一次数据库检查：如果这个副本仍然落后，就拒绝这次读取。

以前，记录工作和全量区工作走两套调度器。各自都能合并自己那一类工作，却不能合并另一类。他们换成了一个统一调度器：规划器决定必须构建什么，调度器决定什么时候可以跑。

假如同一个区在开建之前又来了几条事件：`www.example.com` 的 A 记录变更要求重建这个名字；`*.example.com` 的通配符变更要求重建那个名字并更新共享元数据。调度器会把两个名字和元数据更新合并成一次构建。合并只增加工作：任何一条事件要求完整区，合并后的构建就变成全量；purge 覆盖所有重建，因为它期望的结果是「这个区不再被发布」。

调度器把两样东西分开跟踪：必须执行的 DNS 工作，以及等待确认的 Kafka 消息。重试时两样都保留。即使一次全量构建或 purge 已经不再需要那些个别记录名，消息仍然挂在结果上，直到写入安全完成。换句话说，工作清单可以被吞并或覆盖，ack 清单不能因此变短。

2022 年计划过的那套「先攒一批再构建」的批处理，在统一调度器面前变得没有必要：它不会为了凑批次而等待，只在同一个区已经有工作排队时才合并新事件。

## 4. Soft commit：完成可以乱序，提交位移必须是前缀

一次很慢的构建，即使还有空闲 worker，也可能拖住不相干的客户。Kafka 把消息分成有序的分区，每个分区保存一个 committed offset：这一点之前的每条消息都已知完成。如果把这个位移推过尚未完成的工作，重启之后就可能丢掉一次客户变更。

他们使用的办法叫 soft committing。Fattouche 在 2020-09-15 的 [Secondary DNS - Deep Dive](https://blog.cloudflare.com/secondary-dns-deep-dive/) 里已经写过同一思路。当时的场景是 Zone Transferer 并发处理区传送：Kafka 只是一条 FIFO 队列，并发读者可能先完成并提交中间的消息；Kubernetes 的 pod 又是会消失的。如果先提交了 offset 2、再重启，offset 1 对应的那次传送就再也不会发生。2020 年的算法是：在内存里按 offset 维护一份已读消息的有序列表；传送完成时从列表里拿掉它；只有当它是列表里最老的那一条时，才真正提交这个 offset。2026 年把它用在 Zone Builder 上，表述几乎没变：一次构建可以乱序完成并在内存里被标成完成，但 Kafka 的提交位置只有在它前面的每条消息也都完成之后才向前移动。

![Kafka 分区上 offset 1 已提交，offset 2 仍在运行并挡住水位，offset 3 到 6 已在内存中完成但不能提交；若此时进程重启，内存中的完成标记消失，将从 offset 2 重放](/posts/dns-build/soft-commit.svg)

Secondary DNS 那篇文章还补了一句分布式条件下的前提：这件事要在多副本里成立，Kafka 消息应当按 zone id 做 key，以保证同一个区总是由同一个消费者处理。2026 年这篇没有重述分区键是怎么选的，所以我只把它记成 2020 年已经写明的约束，不去断言今天的 Zone Builder 一定沿用同一个 key。

下面这段 Go 是我写的示意，用来演示「乱序完成、只推进连续前缀」。它不是 Zone Builder 的源码，也没有去连一台真的 Kafka。我用 Go 1.27.3 跑过，输出是这次实际得到的。

```go
// 非官方实现 / 示意：演示 Kafka 分区上的 soft commit 低水位。
package main

import "fmt"

// committed 是「此前每条消息都已完成」的最大 offset。
// 只有连续完成的前缀推进后，才允许把 Kafka 的 committed position 往前移。
type SoftCommit struct {
	committed int
	done      map[int]bool
}

func NewSoftCommit() *SoftCommit {
	return &SoftCommit{done: make(map[int]bool)}
}

func (s *SoftCommit) MarkComplete(offset int) {
	s.done[offset] = true
	for s.done[s.committed+1] {
		s.committed++
		delete(s.done, s.committed)
	}
}

func main() {
	sc := NewSoftCommit()
	for _, off := range []int{1, 3, 4, 5, 6, 2} {
		sc.MarkComplete(off)
		fmt.Printf("完成 offset %d 后，已提交水位=%d，重启将从 %d 重放\n",
			off, sc.committed, sc.committed+1)
	}
}
```

实际输出：

```text
完成 offset 1 后，已提交水位=1，重启将从 2 重放
完成 offset 3 后，已提交水位=1，重启将从 2 重放
完成 offset 4 后，已提交水位=1，重启将从 2 重放
完成 offset 5 后，已提交水位=1，重启将从 2 重放
完成 offset 6 后，已提交水位=1，重启将从 2 重放
完成 offset 2 后，已提交水位=6，重启将从 7 重放
```

offset 3 到 6 尽管先完成，水位仍停在 1；直到挡住前缀的 2 结束，水位才一次跳到 6。若在 2 仍未完成时进程重启，内存里 3 到 6 的「已完成」标记会消失，Kafka 仍停在水位 1，于是从 2 重放到 6。官方原文把这个取舍写得很干脆：他们故意选择重复劳动，而不是丢掉一次变更。

定向规划的价值，在这里不只是「少读一些记录」，还包括缩短「分区上最老那条未完成消息」卡住的时间。调度器另外还防止一个繁忙的区占走所有 worker：一个区构建完成后，它的下一次构建要等待一段按 Cloudflare 方案而不同的重建间隔（rebuild interval）；间隔里到来的变更会被合并进下一次构建。调度器通常执行这个间隔，但若排队的工作已经太老、快要塞住整个 Kafka 分区，它会让这些工作先跑。区锁和重试延迟仍然有效，失败的构建不会在紧密循环里反复执行。

重放之所以安全，和第一节里全量构建的那个「有用性质」是同一件事：构建的真相来源是当前数据库状态，事件主要用来缩小工作范围，而不是当作一份必须按顺序应用的补丁。消息被重放时，规划器会再看一遍现在的库；它可能合并、升级、降级成 purge，或直接跳过，但不应把一条过期事件当成「还要再写入一次旧值」。

## 5. 怎样证明定向输出等于全量输出

更小的构建只有在产出同一份 DNS 数据时才有用。他们为 nameserver、通配符和顶点路径加了等价测试：每一次测试都从同一份数据库状态分别跑全量和定向构建，固定住依赖时间的值，再逐字节比较定向计划所拥有的每一个 Quicksilver key。规划器和调度器的测试覆盖分类、同名区、合并、purge 和升级。上线期间，他们还曾在每一次定向构建旁边再跑一次全量并比较输出。这按设计就是昂贵的——每次都要读完整的区——所以只用到后面的镜像比较能提供同样的信心为止。

测试无法穷尽客户的每一种组合，于是每个发布也会经过一个镜像 Zone Builder。它消费生产环境的 Kafka 流、读取生产环境的数据库状态，但写入另一套不服务任何客户流量的 Quicksilver。比较器抽查 20% 的区，寻找缺失的 key、多余的 key，以及取值不同的 key。两套环境并不总在同一瞬间构建同一个区，所以一次暂时的不一致并不自动等于回归。他们寻找的是：两边都赶上之后仍然留下来的、新类型的差异。

他们为此做了 DNS Mirror Dashboard，用来归类这些差异并保留调查用的例子。文章写明它跑在 Cloudflare 开发者平台上：一个 Worker 接收结果，Durable Objects 保存状态，Cloudflare Access 负责保护。正文对截图的描述是：在 234,313 个匹配的区上，差异率为 0.31%。差异率的定义是：比较发生的那一刻，生产和镜像至少在一个 key 上意见不同的区所占比例。其中多数是两边管道赶上之后就会消失的时间差，所以他们盯两件事：差异率保持低位，以及不再出现新种类的差异。

镜像结果保持健康之后，他们按区名字的哈希逐步放开统一调度器，而不是按区 ID。对名字而不是 ID 做哈希，是为了让共享同一个名字的所有区落在同一套调度器上，避免两套调度器同时写同一把元数据 key。他们先提高免费区的百分比，再对付费区重复同样的过程。

这套发布方式本身就在重申规划器的哲学：增量路径默认不被信任，直到有人和全量路径并排跑过、并且按 key 对过字节。

## 6. 官方数字该怎么读，以及全量构建为什么还在

下面这些数字全部来自 Fattouche 的 2026-11-02 文章，是 Cloudflare 自己的测量。我没有复现它们，也不把它们写成对单个区的延迟承诺——作者自己也写了，这些数字混合了每一种构建类型和每一种客户方案。

在 24 小时里，86.81% 的构建是 Resources only，2.54% 是 Resources and metadata，2.30% 是 Apex and metadata，1.30% 是 purge。加起来，92.95% 的构建避免了重建整个区；全量构建是剩下的 7.04%。两种元数据构建以前都是全量，即使对大区也是如此，它们合计 4.84%；再加上仍然全量的 7.04%，是 11.88%，所以全量构建大约减少了 40%。次数上的份额还低估了省下的工作量，因为被挪走的那些里包括最大的区。留下来的全量构建平均只要 0.35 秒，因为仍然触发它们的事件——比如一个区第一次被发布——大多落在记录很少的新区上。

作为对照，2022 年他们写过：当时还不能完全去掉全量构建，全量大约占 DNS 构建总数的 13%，对应那些必须了解整个区内容的 DNS 设置变更。2026 年的 7.04% 和当年的 13% 不是同一份 24 小时样本里的前后对比，不宜直接相减；上面那句「大约减少 40%」依据的是 2026 年这 24 小时里「以前会走全量的两类元数据构建 + 仍然全量的构建」和「现在仍然全量的构建」之间的关系。

以前，一次很长的全量构建会拖住它所在分区的已提交位移。这类构建变少之后，他们现在可以按事件到达的速率消费 Kafka，而不再落后、再以最高约每秒 1,550 条消息的突发追赶。文章里两张图的描述是：生产速率大致保持在每秒 600 到 800 条；改动前消费在大约 300 到 1,550 之间摆动，改动后消费跟着生产走，大约也是每秒 600 到 800 条。

构建完成延迟是从一条 DNS 记录或区域设置变更，到 Zone Builder 写完 Quicksilver 的时间。生产环境跑旧调度器，镜像在同一组事件、同一段 24 小时上跑统一调度器，两边消费同一份 Kafka、读同一份数据库、向 Quicksilver 写入等价的数据。作者把它称作一次受控的并排比较。这段时间里有很大一部分是前面说的重建间隔，而不是构建本身的计算。典型延迟几乎没变，因为大多数构建本来就已经很小；差别在尾巴上：最大的 p99 尖峰从 14.6 分钟降到 1.21 分钟，约 12 倍。

定向构建也让他们远不那么频繁地装入完整的大区。部署主动使用的工作集内存，平均从 49 GiB 降到 7 GiB，降幅 86%；峰值从 79 GiB 降到 12 GiB，降幅 85%。标题里的「cut memory use by 85%」指的就是峰值这一档。

这些是新调度器的直接结果，也让他们能回头看两条一直为韧性准备的等待。第一条是重建间隔：构建更便宜、完整读入一个区的次数少得多之后，他们可以在大多数方案上安全地缩短它。第二条是 DNS Kafka Aggregator 为了等数据库副本赶上而扣住每条事件的时间：一旦数据库开始拒绝从已经落后的副本读取，这段缓冲也可以更短。两者合在一起，把中位构建完成延迟大约减半，从约 7.7 秒降到约 3.3 秒。图上的第一级下降来自 Aggregator 的改动，中位大约从 7.7 秒落到 6.4 秒；随后带着更短重建间隔的 Zone Builder 发布被一条红带标出，因为是逐步铺开的，延迟又分两步落到约 3.3 秒。同一张图上，p90 大约从 10 秒降到 7.4 秒，p99 看起来停在大约 27 秒附近。

作者特意提醒：后两个百分位没有看起来那么精确。当时的直方图桶在 1、5、10 和 30 秒，落在两个桶壁之间的百分位会被当成延迟在这个区间里均匀分布来估算。大多数延迟其实靠近区间底部，所以这些估计偏高：p99 读起来接近 30 秒，p90 高于 7 秒。不依赖分桶的精确平均值确认了「减半」这件事。他们后来换成了会自动选择细粒度桶的原生直方图：中位大约 3.4 秒，p90 大约 5.5 秒，p99 大多在 10 到 14 秒之间，另一处汇总写成大约 12 秒。

2022 年他们计划彻底消灭全量构建。2026 年的结论是：这既不现实，也没有用。一个区第一次被发布，需要写下每一条记录；一次可能影响区里任何地方的变更，需要检查每一条记录；一条没说清楚改了什么的事件，仍然走全量，因为规划器从不把不确定性翻译成更少的工作；对小区来说，全量构建也很便宜。他们会继续把更多事件挪到定向构建上，但最大的收益已经落下来了：从前会重建最大那些区的事件不再这么做，留下来的全量构建大多由第一次发布这类事件触发，落在又新又小的区上。

## 7. 我的看法

1. **真正难的不是「增量」，而是「证明少做仍然正确」。** 编译器的增量编译、构建系统的缓存、物化视图的增量维护，和这篇里的规划器是同一种形状：先算一份保守的失效集合；证明不了这份集合完整，就退回全量重算。Bazel 一类系统里，未声明的输入会让增量结果静默错误；Cloudflare 把同一风险写成一条可执行的验收标准——定向输出必须和全量输出字节级一致，否则不要走捷径。策划这件事花掉的时间，远多于后来少读的那些记录。

2. **「只做加法的合并」是「不确定就全量」的对偶。** 规划器拒绝把不确定性翻译成更少的工作；调度器拒绝在合并时丢掉任何一项已证明必要的工作，只有 purge 可以覆盖重建，因为它代表一种更强的期望状态。工作集合按并集变大，ack 集合按并集挂住，两边都没有「取巧的减法」。这很像把每个区上的脏名字做成集合，合并就是集合并。2022 年设想过先攒批次再开建；统一调度器选择了另一条路：不为凑批而等待，只在已经排队时合并。对延迟敏感、又必须避免重复全量的管道，这比定时 batch 更老实。

3. **Soft commit 是消费者一侧的「至少一次」，而重放能成立，是因为事件不是补丁。** Kafka 的 committed offset 必须是一个完成前缀，不能因为后面的消息先做完就跳过中间的洞，就像不能确认 TCP 流中间的一段而把前面的空洞留着。重启时用重复劳动换不丢变更，是至少一次投递的老取舍。它能用在 DNS 构建上，关键前提是：构建从当前数据库重算，而不是把事件内容当作要应用到边缘的增量补丁。事件负责缩小范围，数据库负责给出答案。如果有人把这套低水位照搬到「按消息内容做非幂等写入」的消费者上，重放就会变成重复副作用，而不再只是重复劳动。

4. **它仍可能出错的地方，文章自己已经点名了。** 分类若漏掉某项设置会影响区里其他名字，定向构建就会少写或写错 key，这正是等价测试和镜像比较要防的事。同名区共享的元数据 key 是一个天然的写冲突点，所以他们按名字而不是区 ID 做哈希灰度，让共享一名的区落在同一套调度器上。事件可能先于副本可见，所以 Aggregator 要延迟，落后的副本要被拒绝读取。超过记录数阈值就不再升级到全量，是一个被明确承认的缺口：正确性依赖排队事件点出所有受影响的名字，以及 zone hold 降低同名多区的风险，残余情况要靠手工重建个别名字。只更新时间戳的事件仍然走全量，说明生产者一侧的可观测性不完整，会直接泄漏成浪费掉的工作。连百分位数字怎么被直方图桶抬高，作者都写进了正文——读官方延迟时，应当连同这段一起读。

5. **可迁移的不是「五种 DNS 构建」，而是那组分家的职责。** 规划器回答「必须做什么」，调度器回答「何时可以跑、如何合并」，Kafka 消息列表回答「什么时候能确认」；事件时做一次保守规划，执行前再对新鲜快照规划一次；分类默认失败则升级，并用字节级比较做持续集成；用镜像消费者在生产流量上验证增量路径，再用名字哈希保证共享状态不会被两套调度器同时写。这些对别的「从控制面投影到边缘」的管道都用得上：配置下发、证书分发、规则编译、搜索索引的部分更新。DNS 只是让错误代价足够高，因而把「证明」写成了第一公民。

6. **放弃「消灭全量构建」，是这篇比 2022 年更成熟的地方。** 第一次发布、可能影响任意记录的变更、说不清楚的事件，本来就应当读完整份区；小区上这么做也很便宜。增量系统常见的幻觉是把全量当成耻辱，于是在无法证明安全时仍然坚持走捷径。Cloudflare 选择把大区从全量路径上拿下来，同时承认全量是一种仍然便宜、仍然必要的工具。标题里的 85% 和「减半」都应该当作官方自测来引用；对设计更有用的，是那句不带倍数的原则：规划器从不把不确定性翻译成更少的工作。
